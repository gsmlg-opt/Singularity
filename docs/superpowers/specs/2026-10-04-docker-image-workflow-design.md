# Docker image workflow design

Date: 2026-10-04

Status: approach approved; written specification awaiting user review.

## Goal and boundary

Add an image-only GitHub Actions workflow with manual inputs and automatic
publication when a GitHub Release is published. Preserve the existing
`release.yml` source preparation, versioning, OCI archive verification, and
release publication without modification.

The existing registry remains `ghcr.io/gsmlg-dev/singularity`, authenticated with
the existing `GHCR_TOKEN` secret. Creating the workflow does not authorize a
dispatch, image publication, product release, push, deployment, version bump,
or acceptance of an unfinished `0.2.0` phase. No application, migration,
Dockerfile, or Vault behavior changes are included.

## Trigger and input contract

The new file is `.github/workflows/docker-image.yml`, named `Docker Image`.
It accepts `workflow_dispatch` and `release: types: [published]`; no push,
pull-request, or scheduled publishing trigger is added.

Manual inputs:

| Input | Type | Behavior |
| --- | --- | --- |
| `tag_name` | required string | Exact named Docker tag to publish. |
| `git_ref` | required string, default `main` | Repository branch, tag, or commit SHA to build. |
| `generate_latest` | boolean, default `true` | Also promote the verified image to `latest`. |

For release events, use the release's `tag_name` for both the named image tag and
the source Git tag. Resolve the actual tag commit, not `target_commitish` or the
default branch. A prerelease publishes its named tag but never automatically
updates `latest`. A stable release may update `latest` only when it is still the
repository's designated latest stable release at promotion time. A failure to
verify release state stops promotion rather than assuming eligibility.

Validate Docker tags without silently rewriting them: one leading ASCII letter,
digit, or underscore, followed by up to 127 ASCII letters, digits, underscores,
periods, or hyphens. Reserve `latest` as an alias, not an independent `tag_name`,
so `generate_latest=false` cannot be bypassed. Invalid or unresolved refs fail
before building or publishing. Inputs are passed as environment variables or
action inputs, never interpolated directly into executable shell code.

## Source, build, and promotion

1. Check out the selected repository ref without persisting Git credentials.
   Resolve and record the full commit SHA and use only that checkout for the
   build. For release events, resolve `refs/tags/<release tag>` to a commit and
   require both it and the checkout to equal the event's `github.sha`. A moved
   tag or mismatch fails closed instead of silently building different source.
2. Use the existing pinned Docker action, QEMU/binfmt, and BuildKit versions.
   Build the root Dockerfile for `linux/amd64,linux/arm64`, with provenance and
   SBOM generation and an image-workflow-specific cache scope.
3. Set Docker build arguments `VERSION` to the named image tag and `REVISION` to
   the resolved full source SHA. These are image metadata; do not edit Mix's
   application version or create a Git tag.
4. Push immutable content by digest first, without promoting named aliases.
5. Verify that the build action and build metadata agree on a valid SHA-256
   digest; inspect and hash the registry's raw manifest to verify that digest.
   Require exactly the intended amd64 and arm64 runnable platforms and valid
   provenance/SBOM attestation relationships. No OCI archive is generated by
   this image-only workflow.
6. Promote the verified immutable digest to `tag_name` and, when eligible,
   `latest`. Both aliases refer to the same content. Do not replace the existing
   release workflow's minor-version alias policy or add new tag families.
7. Record the source SHA, named tag, immutable digest, platforms, and whether
   `latest` was updated in the workflow summary. Do not expose credentials.

Use explicit least-privilege permissions: repository contents read and package
publication write. No repository contents-write or Git tag/release creation is
needed. Keep credentials out of build arguments, labels, image layers, and logs.
Apply a bounded job timeout and stop on failed builds, source checks, digest
checks, or required GitHub API requests.

Use workflow-level concurrency `group: Release` with
`cancel-in-progress: false`. This matches the existing Release workflow's
resolved concurrency group and serializes registry promotion across both paths
without changing `release.yml` or cancelling an in-flight publication.

## Existing release integration

The existing Release workflow already builds, verifies, and promotes Docker
images before creating the GitHub Release using `GITHUB_TOKEN`. GitHub does not
start downstream `release: published` workflows for events created with that
token. Therefore this existing path remains covered by its own verified image
publication, without a redundant rebuild or an explicit additional dispatch.

Human-, GitHub App-, or PAT-published releases can invoke the new release-event
path. Document this distinction and the existing cross-organization registry
secret requirement. The workflow must exist on the default branch before manual
dispatch can be used.

References: [GitHub workflow triggering rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
and [release event source identity](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release).

## Implementation scope and verification

Implementation is limited to the new workflow, focused image-workflow
architecture contracts, and Docker deployment usage documentation. Add the new
workflow to the explicit actionlint enumeration in README and its synchronized
release/container contract; preserve all existing required verification commands
and assertions. Update only the matching actionlint file list in
`docs/superpowers/plans/2026-08-31-singularity-v0.2-release.md`, not its product
gates or phase scope.

First add failing focused contracts for the new triggers, inputs, source
resolution, safe input handling, permissions, digest-before-promotion ordering,
platform coverage, shared concurrency, and `latest` policy. Exercise invalid
tags, unresolved refs, prereleases, older stable releases, API failures, and
digest disagreement without network publication. Keep existing release contracts
passing without weakening their assertions.

Run only the focused image/release contracts, formatting for changed tests,
actionlint for the affected workflows, shell syntax checks, and `git diff --check`.
Record exact commands, results, changed files, source commits, and remaining
risks. Do not run browser/E2E tests, dispatch GitHub Actions, push an image, push
Git changes, or claim multi-platform build or release acceptance from static
checks. No new product phase or backup compatibility is accepted by this work.
